# Лоция: автоматизация повседневной работы

Рабочее предложение от 26 октября 2026 года. Это план развития, а не перечень уже реализованных функций. Проверенный новый сценарий разделов опубликован отдельно в публичной Лемме; производственная Лоция остаётся на установленной пользователем версии .206.

## Исходные условия

- Документы остаются в файловой шаре. Для Лоции она доступна только для чтения, с обычными правами пользователя.
- Состав проекта задаёт ГИП или РП. Типовая структура папок помогает начать, но допускает изменения.
- Работа должна продолжаться при временном отключении сети. Последний успешный реестр сохраняется с датой проверки.
- Автоматизация работает по явным правилам и данным системы. ИИ для этих сценариев не нужен.
- Принятие результата, выдача документации и изменение ответственных остаются явными действиями людей.

## Первый полезный выпуск

Сделать один законченный сценарий: «Создать проект → выбрать состав разделов → подтвердить команду → получить задачи и проверки в личной очереди».

1. Состав разделов и команда редактируются на отдельном понятном экране. Можно добавить свой раздел, убрать и вернуть прежний без потери связей.
2. Повторное создание проекта предлагает сохранённый пользователем шаблон состава. Шаблон не переносит историю, сроки и закрытые задачи.
3. При создании задачи из раздела проект и раздел уже выбраны. Если у раздела несколько подходящих исполнителей, требуется выбор; назначения не принимаются молча.
4. «Мой день» показывает сначала личные действия, затем текущую работу. Управленческое наблюдение не превращается в чужие личные проверки.

Критерий пользы: проект настраивается без переходов по справочникам, новая задача требует меньше повторного ввода, сотрудник сразу видит, какое действие ждут лично от него.

## Проверка шары: отдельный технический пилот

Начать с одного проекта и двух–трёх согласованных папок с исходными данными и выдачами. Первое чтение создаёт исходный реестр без сотен уведомлений. Следующее чтение показывает только разницу.

Обязательные правила:

- Полный успешный обход и неполное чтение имеют разные статусы. Недоступная папка не означает, что файлы удалены.
- При обрыве связи сохраняются привязка и последний успешный реестр. Повторная проверка продолжается автоматически с ограничением частоты.
- Базовая сверка использует путь, размер и время изменения. Контрольная сумма считается отдельно, когда нужна точная фиксация содержимого. Совпадение имени не доказывает совпадение версии.
- Переименование нельзя надёжно отличить от удаления и добавления только по путям: показывать это как требующее сверки изменение, пока идентичность не подтверждена.
- Сетевой доступ выполняет процесс под согласованной учётной записью пользователя. Браузерные права сами по себе не дают серверу доступ к UNC-папке.
- Сканер ничего не пишет в шару. Привязки, наблюдения, результаты сверки и журнал хранятся в Лоции.
- Длительные обходы идут в фоне, с лимитами и возможностью повторить. Параллельные запуски не создают дубли реестра.
- Для факта выдачи требуется отдельная подтверждённая запись. Новая папка или изменённый PDF сами по себе не закрывают задачи.

Критерий готовности пилота: отключить шару во время обхода, включить обратно, проверить сохранность привязок и истории; доказать отсутствие ложных удалений, дублей и записи в исходные папки.

## Техническая опора

В публичном исходном коде уже есть `TaskActionQueueService`, `WorkdayService`, `ProjectStructureService`, `NotificationOutboxService` и `ResourceService`. Их можно расширять для очереди действий, контекста задач и событий. Это не доказывает готовность новых сценариев: правила замещения, дедупликация и принадлежность личных действий должны проверяться отдельно.

Часть работы с сетевыми папками находится в частной Лоции и должна проверяться на её точной версии. Публичная Лемма служит прототипом интерфейса, а не доказательством работоспособности Windows/SMB-контура.
